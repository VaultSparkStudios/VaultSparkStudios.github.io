## A1 · The monthly-send safety gate is bypassable by a dropdown, and the branch that holds it has never executed

`.github/workflows/member-newsletter.yml` holds the unarmed monthly send with:

```
if [ "${EVENT_NAME}" = "schedule" ] && [ "${NEWSLETTER_ARMED}" != "true" ]; then
```

Two consequences follow from keying that gate on the **event** rather than on the
**effective mode**:

1. **The arming decision is bypassable.** A manual `workflow_dispatch` with
   `mode=send` sets `MODE=send` and `EVENT_NAME=workflow_dispatch`, so the hold
   branch is skipped entirely and the run mails every opted-in member — with
   `NEWSLETTER_ARMED` still unset. D-S341.4 deliberately left the send unarmed;
   a dropdown selection currently overrides that decision with no gate at all.
2. **The hold branch is unreachable by any manual run.** The one branch S362 added
   to stop the false alarm can only ever be taken by a `schedule` event, so it will
   first execute unobserved on 2026-10-02. A guard that cannot be exercised before
   it matters is not yet evidence of anything.

Both dissolve in the same edit: gate on `MODE = send` regardless of event. That is
strictly safer (it closes the bypass) *and* testable (a manual `send` dispatch now
exercises the exact branch the schedule will take).

**Fix:** hold whenever the effective mode is `send` and `NEWSLETTER_ARMED != true`.

## A2 · The staleness probe cannot say "repaired, awaiting its next run"

`check-scheduled-workflow-staleness.mjs` reports Monthly Member Newsletter
`broken`, `streak: 6`. Both causes of those six failures are already fixed:

- The Sept 2 run failed `HTTP 404 · {"code":"NOT_FOUND"}` — the edge function was
  not deployed. It is deployed now: the Management API lists
  `send-member-newsletter` **ACTIVE v1** (verified live this session).
- The unarmed schedule hard-failed. Since S362 it holds and exits 0.

Every one of the six failing runs predates both repairs. The probe judges a cron
purely on run history, so its verdict cannot clear until the next scheduled
occurrence on 2026-10-02 — twelve more days of a red doctor for a cron that has
already been fixed. During those twelve days a genuinely newly-broken monthly cron
would be indistinguishable from this one.

The missing distinction is cheap and it is already sitting in git: **did the
workflow's own source change after the newest failing run?** If it did, and the
next scheduled occurrence has not yet arrived, the honest verdict is
`repaired-untested`, not `broken`.

It must not become a mute button, so it is bounded on both ends:

- A workflow whose source has **not** changed since the failures stays `broken`.
- A new run that fails **postdates** the change, so the streak is real again.
- The downgrade **expires** one full interval after the repair. If the cron went a
  whole cycle without producing a run, the repair never corroborated itself and
  `broken` returns — silence is not a pass.

**Fix:** add a self-expiring `repairedUntested` verdict keyed on the workflow
file's last-commit time.

## A3 · `overall: blocked` contradicts the invariants published beside it — on a public surface

`api/supabase-control-plane.json` computes:

```
overall: allReady ? 'ready' : dataRestReady ? 'partial' : 'blocked'
```

The entire summary pivots on the **dataRest** plane. Today's receipt reads
`overall: "blocked"` while carrying `managementApi: ready`, `sqlMigration: ready`
and `edgeFunctions: ready` — and, in the same file, the invariants
`serviceRoleDoesNotImplyFunctionDeploy` / `...SqlMigration`, which state outright
that the service-role plane governs none of the other three. The summary and the
invariants cannot both be right.

The consequence is not cosmetic. `blocked` is the single line the CLI prints, and
this receipt is published to `status/`, `agents.json` and `api/release-proof.json`.
A reader who trusts the headline concludes edge-function deploy is unavailable and
escalates a founder blocker — the exact phantom-blocker failure CANON-019 exists to
prevent. This session very nearly did: the one-line verdict said `blocked`, and
deploy authority was live all along (HTTP 200, 30 functions enumerated).

`partial` already exists and already means "some authority, not all". It simply is
not reachable unless dataRest is the plane that is healthy.

Checked before changing: `check-production-promotion-gate.mjs` keys on
`overall === 'ready'` (twice) and on the disclosure reason
`supabase-control-plane-partial`. Widening `partial` therefore cannot loosen the
promotion gate — a `blocked → partial` receipt still fails `=== 'ready'`, and the
held path's required disclosure reason becomes accurate rather than contradicted.

**Fix:** `ready` when all planes are ready · `partial` when **any** is · `blocked`
only when none is. Name the live authorities on the CLI line.
