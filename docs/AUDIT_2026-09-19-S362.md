## 1 · [OBS · P1] The cron parser cannot read a cron line that carries a comment

**Measured live:** `check-scheduled-workflow-staleness.mjs` reads cron lines with
`/^\s*-\s*cron:\s*['"]?([^'"\n]+?)['"]?\s*$/`. The trailing `\s*$` makes any line with a YAML
comment (`- cron: '0 6 * * 1'   # Every Monday`) match nothing. That applies to 11 cron lines
in 9 workflows. Those workflows fall back to a 24h interval, so the weekly **Weekly
Maintenance** job (last scheduled run 135h ago, on time) is flagged `silent` against a 72h
threshold. The doctor showed that verdict. The verdict also flickered: 14 workflows were checked on one run
and 11 on the next, so the same repo read red and green a minute apart.

Second defect in the same function: separate cron lines are combined with `min`, so
`news-publish.yml` (four daily slots, a real 6h cadence) is expected once a day, and a stall
of up to 72h would go unreported.

**Do:** parse the cron field up to the closing quote or a comment; combine lines by summing
their rates (`1 / Σ 1/interval`). Add fixtures for both cases, taken from the real workflow text.

## 3 · [PRODUCT · P1] No gate installs the service worker in a real browser

**Premise (S361):** the worker went `redundant` on every production install from at least
2026-06-03 to 2026-09-19, and no gate caught it. `verify-sw-assets.mjs` checks that the
precache files exist on disk, and the S361 unit test rejects duplicate entries. Neither one
runs `navigator.serviceWorker.register()`.

**Do:** add `tests/service-worker-install.spec.js`. Against the local preview it registers
`/sw.js`, waits for the `activated` state and asserts that the precache holds every declared
entry. Wire it as a **blocking** step in the E2E compliance job, which already runs against
the local preview, and add it to the `verify:local` core tier.

## 4 · [OPS · P2] The unarmed newsletter cron fails every month by design

**Measured live:** 6 consecutive scheduled failures, most recently 2026-09-02:
`404 Requested function was not found`. D-S341.4 and the S354 founder directive keep
the newsletter unarmed until the founder chooses to arm it. The cron still fires, fails and
keeps the doctor red, so a real broken cron would look like this known one.

**Do:** the scheduled trigger checks the repository variable `NEWSLETTER_ARMED`. If the
variable is not `true`, the run emits `::warning title=Member newsletter held::` and exits
successfully. The staleness probe already reports held runs by name (S355), so the state stays
visible and does not read as green. The manual dispatch modes are unchanged. Arming = set the
variable (documented in the workflow and in the decision). This change sends nothing and
arms nothing.
