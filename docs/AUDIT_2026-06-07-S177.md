## Diagnosis — what the failing probe actually told us

S176 shipped a first-party uptime probe (`scripts/probe-uptime.mjs` + `uptime-probe.yml`, */30,
Resend alerts). Its first cron run (2026-06-07T21:43Z) failed: `/` → 403, four HTML routes →
30s timeout, `/api/founder-presence.json` → 200, then it emailed the founder "5 routes failing."

Forensics (live, this session):

| Probe path | Result | Meaning |
|---|---|---|
| `vaultsparkstudios-website.pages.dev/` (Pages origin, browser UA) | **200, 0.6s** | Origin/build healthy |
| `vaultsparkstudios.com/` (scanner UA `curl/8`) | 403, 0.35s | Worker scanner shield — **reached Worker** (tail confirms) |
| `vaultsparkstudios.com/api/*.json` (browser UA) | 200 | Edge + Worker chain alive |
| `vaultsparkstudios.com/` (browser UA, `Accept: text/html`) | **hang / 000** | **Never reached the Worker** (tail confirms no invocation) |
| `vaultsparkstudios.github.io/` (GH Pages rollback) | 301 | Rollback origin healthy |

`wrangler tail` (live) logged the scanner and JSON requests but **not** the browser-UA HTML
request — proving HTML navigation from datacenter IPs is intercepted **at the Cloudflare edge,
before the Worker**: a bot / managed challenge. Real residential browsers solve it transparently
(JS clearance); curl / headless / GitHub Actions cannot, so they hang.

**Verdict: the site is UP for real users.** The probe was DOA — it measured "can a datacenter IP
pass the bot gauntlet," not "is the site up," and is now phantom-paging the founder every 6h/route.

A second, real weakness surfaced while reading the Worker: S176's disaster-recovery failover only
fires on a clean `5xx`. An origin **hang** (no status — the more common real failure, and exactly
the shape the founder saw on 2026-06-07) is never caught, because the primary `fetch(req)` in
`originFetch` has no timeout. The Worker would block until the edge wall-clock limit.

## Ranked plan

### 1 · [P0 · OBSERVABILITY] Probe real availability, not bot-gauntlet-passing
`probe-uptime.mjs` is rewritten to measure what real users experience:
- **Content availability** — fetch each HTML route from the Pages origin
  (`vaultsparkstudios-website.pages.dev`), which is unchallenged → true build/content health.
- **Edge liveness** — fetch a custom-domain JSON endpoint (DNS + Cloudflare + Worker chain).
- **Informational** — the custom-domain HTML request is kept as a short, **non-alerting** probe so
  the dashboard records the challenge state without paging.
- **Alert only** on real origin-route failure or edge-liveness failure. The challenge never pages.
- Self-test extended to cover the new classifier (challenge != outage).
Stops phantom founder alerts **and** makes the probe actually detect outages (it currently can't —
it 100% false-positives, which is worse than no probe).

### 2 · [P1 · RESILIENCE] Worker: fast-fail an origin hang into existing failover
Add `AbortSignal.timeout` to the primary origin fetch in `originFetch`. A hang now degrades to the
pages.dev failover -> DR-cache path that S176 already built, instead of blocking the Worker. Directly
hardens the disaster-recovery layer against its most likely real trigger.

### 3 · [P1 · KNOWLEDGE] Capture the bot-challenge diagnostic
DECISIONS entry + agent memory: prod HTML nav is edge-bot-challenged; datacenter/CI/curl clients
hang or 403; **this is not an outage**; verify true availability via the Pages origin + a JSON API
path. Prevents the next agent from burning a session re-diagnosing "the site is down" (this session
nearly did).

### 4 · [P2 · EFFICIENCY] Probe runtime
The failed run burned 4m14s (30s hangs × routes × retries). The new design + short informational
timeout keeps a run well under 30s and stops wasting Actions minutes on the unsolvable challenge.
