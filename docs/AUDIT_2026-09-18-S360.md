## 1 · [OBS/UX · P1] /status/ cannot tell a provider outage from a site fault, and has no sign-in row

**Measured live (S360):** Supabase `fjnpzjjyhnpmunfoycrp` health API reports db/rest/auth
`UNHEALTHY`; every anon REST call and `/auth/v1/health` times out at 12s. `/status/` turns
three cards red after its 5s timeout, headed "Partial Outage Detected" — and says nothing
else. A visitor cannot learn that the website is fine, that the fault is at the database
provider, or which features they will feel (comments, member data).

**Also:** `pingVault`/`pingDB`/`pingGameSessions` accept `401`/`403` as "operational". The
Supabase gateway answers 401 in ~50ms *while the database is unreachable* (measured: 401 in
0.05s with no apikey during this outage), so a rejected-key response can paint green over a
dead database. Only a real 2xx body (or a 206 range) proves the REST→DB path.

**Outcome:** info-finding — a visitor on /status/ during an outage learns what is broken,
whose fault it is, and what still works, instead of a bare red banner.

**Do:**
- Add a **Member sign-in & data (Auth)** card probing `/auth/v1/health` with the publishable key (200 ⇒ up).
- Stop treating 401/403 as proof of life on REST probes that the anon role can read; keep
  403-as-alive only for `investors` (RLS-denied by design) and label it "gateway reachable".
- When every Supabase-backed probe fails together, show a provider-attribution line:
  "Our database provider (Supabase) is not responding. The website is up; comments, member
  profiles and leaderboards are affected." — derived from the results, never hard-coded.
- Link the Desk comments "temporarily unavailable" state to `/status/` so the reader has somewhere to go.

**Ladder:** L1 0.5h attribution line · L2 1h + auth card + honest status codes · L3 1.5h + comments link + rendered-pixel receipt.

## 2 · [UX/A11Y · P2] Leaderboard embed inherits host theme tokens over its own fixed dark ground

**Verified:** `api/leaderboard/v1/widget.js` paints `background:#0a0a0a` but colours its rank,
runtime, empty-state, brand and footer text with `var(--muted,#a8b4d0)` / `var(--dim,#6e7fb0)`.
On any host page that defines those tokens — including our own `/api/leaderboard/` in light
theme (`--muted:#334155`, `--dim:#475569`) — the text lands at ~1.7:1 and ~2.4:1 on near-black.
The board's S356 premise ("#555/#666 greys") is stale; the defect moved, it did not go away.

**Outcome:** conversion — the embed is the studio's off-site acquisition surface; unreadable
ranks on a host page are a dead link-back.

**Do:** scope the widget to its own literal palette (an embed must not read host tokens),
verify each pair ≥ 4.5:1 on `#0a0a0a`, and add a unit check that the widget CSS contains no `var(--`.

## 3 · [GATES · P3] `build-shell-assets` runs its build on import (from TASK_BOARD, S359)

**Verified:** `scripts/build-shell-assets.mjs:550` calls `main()` unconditionally, so importing
the pure helper `predicatesMissingShellAsset` rewrites every HTML page and the service worker.
That is why S359 could not give the helper a self-test.

**Outcome:** prevents a silent fingerprint drift reaching production (a stale shell asset is a
broken page for returning visitors).

**Do:** guard `main()` behind an `isMain` check (the idiom in `build-intent-map.mjs:147`), add a
`--self-test` with fixtures (listed-and-present, listed-and-missing, missing block, commented
entry), and wire it into `test:unit`.
