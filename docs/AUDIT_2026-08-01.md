# Audit — 2026-08-01 (Session 301)

**Scope:** finish the Obelisk identity lane started in S300. Every premise below was
verified against **live** production systems (Supabase management API, the production
Cloudflare Worker, the deployed edge-function bundle) before it was ranked. No item is
carried from a prior document without re-verification.

**Headline.** S300 landed Obelisk SSO on production and left three identity blockers on
`api/identity-migration-receipt.json`. One of them (`real-provider-e2e-pending`) is
genuinely founder-gated. The other two were labelled human-blocked because three Supabase
credentials were absent from the gateway — **they are present now**, and the control plane
probes `ready` on all four authority planes. The work those blockers were holding is
therefore agent work under CANON-019/CANON-040, and one of them is masking a live
entitlement regression against a paying member.

## Ranked plan

### 1 · [IDENTITY/P0] Eternal tier is locked out of the content it pays for

**Premise — LIVE-VERIFIED, not inferred.** `pg_get_functiondef` on production returns, for
`public.get_classified_files`, `public.claim_beta_key`, and the `beta_keys` SELECT policy,
the narrow predicate `v_plan = 'vault_sparked'`. The committed migration
`supabase/migrations/20260723_fix_classified_archive_entitlements.sql` widens all three to
`in ('vault_sparked', 'vault_sparked_pro')`.

**Impact is real and countable.** `subscriptions` holds **1 active `vault_sparked_pro`**
(Eternal) subscriber; `classified_files` holds **1 row with `required_plan =
'vault_sparked'`**. A member on the highest paid tier is served `content_html = ''` and
`locked = true` for content their tier is supposed to inherit. `beta_keys` is empty, so the
policy and RPC halves of the fix are correctness-only today.

This is not "a pending migration". It is a live entitlement defect whose fix has been sitting
committed for nine days behind a credential that now exists.

**Authority:** `sqlMigration` plane `ready` — management API `POST /database/query` returns
201 for a read-only `select 1`. Migration body is `create or replace` + `drop policy if
exists`/`create policy` — idempotent and re-runnable.

**Risk:** `create or replace function` fails if the return signature changed. The live
`RETURNS TABLE(...)` was read and compared column-for-column against the migration's — they
match. Apply must still capture a pre-image so rollback is exact rather than described.

### 2 · [IDENTITY/P0] The deployed `eternal-intelligence` function is drifted from source

**Premise — LIVE-VERIFIED by byte-search of the deployed bundle.** `GET
/v1/projects/{ref}/functions/eternal-intelligence/body` returns a 359,339-byte ESZIP.
`getActivePlanKey` is present at offset 2439; **`website.staging.vaultsparkstudios.com` is
absent entirely**. The deployed build predates the `buildCors` staging-origin allowance in
`supabase/functions/eternal-intelligence/index.ts`. Deployed version 3, updated 2026-04-21.

`[functions.eternal-intelligence] verify_jwt = false` is correctly pinned in
`supabase/config.toml` and matches live gateway posture — that part needs no change.

**Authority:** `edgeFunctions` plane `ready`.

### 3 · [TRUTH/P0] The identity receipt's only input is a hand-typed file

`context/IDENTITY_MIGRATION_EVIDENCE.json` carries `runtimeUpdates.*.deployed` and
`.verification` as literal booleans/strings. `scripts/build-identity-migration-receipt.mjs`
derives the **public** receipt faithfully from whatever those fields say — and nothing
anywhere verifies them against a provider. Two production blockers can currently be cleared
by editing prose.

This is the item that makes items 1 and 2 safe to do. The fix is not "be careful when
editing the file" — it is that the runtime facts must be **produced by a live verifier that
re-reads the provider after the write**, so the only way to make the receipt say `deployed`
is to have actually deployed. Ranked P0 and sequenced first for that reason: items 1 and 2
should be executed *through* it, so their evidence is machine-produced by construction.

### 4 · [TRUTH/P1] An unknown capability name is reported as a missing credential

**Reproduced:** `node scripts/check-secrets.mjs --for definitely-not-a-real-capability-xyz`
prints `⛔ MISSING`, `missing:` (empty list), exit 0. There is no capability literally named
`supabase` — the real ones are `supabase.admin` and `supabase.client` — so
`--for supabase` reads MISSING while all four Supabase planes probe `ready`.

This is precisely the phantom-blocker generator CANON-019 forbids: the discovery tool that
exists to *prevent* false human-blocked labels emits one when the caller mistypes or guesses
a capability name. `MISSING` (credential absent, founder action) and `UNKNOWN` (caller error,
agent action) must not share a rendering or an exit code.

### 5 · [TRUTH/P1] The board's account count is stale by 76%

`context/TASK_BOARD.md` says "Link the 143 existing accounts". **Live: `auth.users` = 252,
`obelisk_sub` linked = 0.** A public-adjacent planning number that is wrong by 109 accounts.

### 6 · [IDENTITY/P1] Bulk linking is fabrication; the pre-flight is not

`ensureSupabaseIdentityLink` links on first login by verified email. No `obelisk_sub` exists
for a user who has never signed in — a bulk pre-link would have to invent provider subjects,
which is fabricating evidence to close a task. The task as written is not agent-executable
and saying so is the correct answer.

What **is** agent work is clearing the failure modes before 252 users hit them. The link path
fails closed on `identity_email_duplicate` (two Supabase rows sharing one verified email) and
`identity_email_conflict` (subject and email resolving to different rows). Those are
discoverable now, read-only. **Live: 0 duplicate-email groups across 252 accounts; 2 accounts
with no email (cannot match, cannot conflict); 73 unconfirmed (Obelisk requires
`email_verified`, so a verified provider claim confirms them).** The linking surface is clean
— but nothing in the repo asserts that, and nothing would notice if it stopped being true.

### 7 · [TRUTH/P1] The receipt advertises the wrong environment

`build-identity-migration-receipt.mjs` captures the **first** `OBELISK_REDIRECT_URI` match in
`cloudflare/wrangler.toml`. That is `[env.staging]`'s — production defines no `OBELISK_*`
vars at all and falls through to `DEFAULTS` in `cloudflare/obelisk-auth.js`. So the public
receipt binds `callbackHost: website.staging.vaultsparkstudios.com` while production is the
live relying party, and its worker binding is version `773ec75d…` from 2026-07-24 —
superseded by S300's production deploy. A regex that silently takes the first of two
environments is a coherence bug, not a formatting one.

### 8 · [SEC/P2 · FOUNDER-GATED] Every login pages every user

`scanSupabaseUsers` walks `/auth/v1/admin/users?per_page=100` up to 20 pages **on every
callback**, then throws `supabase_user_scan_limit`. At 252 users that is 3 admin round-trips
per sign-in; at 2000 users **every login fails**. It fails closed, so this is a capacity
cliff at ~8× current scale, not a security hole.

The fix (an indexed `security definer` lookup, additive with fallback to the existing scan)
touches the authentication flow, which `AGENTS.md` puts behind founder escalation. **Recorded
with the design, deliberately not applied.** Escalating is the instruction; quietly patching
auth because the fix looks small is not.
