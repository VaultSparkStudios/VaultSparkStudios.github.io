## Theme — the publisher's other half

Every scheduled publisher in this repo is two transactions, not one: **generate + validate**, then
**land on main**. The repo has invested heavily in the first half — twenty-plus `--check` gates run
inside the uptime publisher alone before it stages a byte. The second half, the git transaction, has
no gate, no contract, and (in eleven of twelve publishers) no recovery. S341 found it failing live.

## NOW

### A1 · [P0 · CI] The uptime publisher's retry loop cannot recover from a rebase conflict

**Status: LIVE FAILURE.** `uptime-probe` has failed every run since 2026-09-03T01:52Z
(runs 33705369509, 33707261102). The public availability surface — `api/uptime.json`,
`api/public-status.json`, `api/status-proof.json`, `api/citation.json`, `data/stats-surface.json` —
has been un-published for the duration.

The conflict is not the defect. This is the defect:

```bash
for attempt in 1 2 3 4; do
  git pull --rebase --autostash origin main || true
  if git push; then pushed=1; break; fi
  ...
done
```

Attempt 1's rebase hits a content conflict in five derived artifacts and leaves the repo
**mid-rebase, detached HEAD**. `|| true` swallows that. `git push` then fails with
*"You are not currently on a branch."* Attempts 2, 3 and 4 each re-enter a `git pull --rebase`
that fails instantly — *"Pulling is not possible because you have unmerged files"* — swallowed
again by `|| true`, followed by the same doomed push. **Three of the four attempts are
structurally incapable of succeeding.** The loop spends fifty seconds re-reporting attempt 1,
then exits 1 claiming it failed "after 4 attempts". It had one.

Second-order: every conflicting file is a *derived artifact this very step regenerated* seconds
earlier. A content merge of a regenerated artifact is meaningless — the correct recovery is to
unwedge, take the freshly generated side, and **re-validate**, because a rebase may have brought
in a new *input*, which is precisely the class S340 had to repair by hand.

**Reuse, don't invent (CANON-039):** `news-publish.yml:288-300` already carries the correct
shape — `git pull --rebase -X theirs` plus `git rebase --abort` in the failure path. It is the one
publisher of twelve that survives a conflict. Adopt it, and add the re-validation step it lacks.

**Verify:** re-run the workflow; assert it lands. Then assert the loop is recoverable by
construction via A3.

### A2 · [P0 · CI] The same defect is in ten more publishers

Twelve workflows run `git pull --rebase` to land a publish. **Exactly one** (`news-publish`) can
recover from a conflict:

| Workflow | retry loop | `rebase --abort` |
|---|---|---|
| `news-publish.yml` | yes | **yes** |
| `uptime-probe.yml` | yes | no — failing live |
| `cloudflare-analytics-pull.yml` | yes | no |
| `sitemap.yml` | yes | no |
| `ci-status-beacon` · `leaderboard-api` · `lighthouse` · `og-images` · `refresh-live-data` · `rum-pull` · `vault-narrative` · `weekly-maintenance` | no | no |

The three with a retry loop and no abort are strictly worse than the eight without: a single-shot
publisher fails once and honestly, whereas a loop that cannot unwedge burns its attempts and
reports a misleading attempt count. Fix the three; give the eight the same recovery so a conflict
costs a retry rather than a run.

### A3 · [P1 · GATE] `check-ci-publisher-resilience` measures one half of the property its name promises

The gate exists, is wired into `build:check`, self-tests, and stayed **green** through all of A1.
Its subject is the *script's* handling of a transient network 5xx. The git-publish transaction —
the other half of every publisher, and the half that actually failed — is outside its subject
entirely. A gate whose name promises a property must measure that property, or the green is worse
than no gate at all: it is an assurance nobody re-checks.

Extend it with a second, structural contract over the workflow YAML: **a publisher that rebases to
land MUST be able to recover from a conflict** — a retry loop containing `git pull --rebase` must
also contain `git rebase --abort` on its failure path. Structural, not a hardcoded workflow list,
so a publisher added next session is covered on arrival.

### A4 · [P1 · OBS] The dead-cron detector's window is 4.6 hours, and it counts "unmeasured" as healthy

`check-scheduled-workflow-staleness.mjs:92` asks for the repo's last **120 runs across all
workflows**, then filters to scheduled ones. Measured live this session: those 120 runs span
**4.6 hours**, because push-triggered workflows dominate them (33 `pages-build-deployment`,
18 `CI Status Beacon`, 9 `Cloudflare Pages Deploy`, …). Of the 14 scheduled workflows it reports
checking, **11 return zero rows**:

> CI Health Monitor · Cloudflare Analytics Pull · Monthly Investor Digest · Investor KPI Snapshot
> (daily) · Draft Monthly Signal Log Revival · Generate Leaderboard API · Monthly Member Newsletter
> · The Desk — Scheduled Publish · RUM Field Pull · Generate Vault Narrative · Weekly Maintenance

A daily, weekly or monthly cron **cannot** appear in a 4.6-hour window. And line 163 classifies
those rows as `!v.broken` — so the probe that exists to catch a dead cron is blind to exactly the
crons most able to die unnoticed, and reports them as fine. A monthly digest could be dead for a
quarter with this probe green the whole time.

Fix: query per workflow so each cron gets its own bounded window regardless of repo churn, and
judge each against **its own cron cadence** rather than a shared clock. Report `unmeasured`
honestly (CANON-031) instead of folding it into the healthy count.
