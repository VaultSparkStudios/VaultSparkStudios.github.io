## A1 · P0 · `refresh-live-data` stages the producer and strands the consumer

**Verified.** `.github/workflows/refresh-live-data.yml` (4-hourly, commits `[skip ci]`):

- Its build step runs `npm run build`, which regenerates **both**
  `api/funnel-summary.json` (via `scripts/rollup-rum-ux.mjs`) **and**
  `.cache/cta-readiness.json` (via `scripts/check-cta-readiness.mjs`). Both are in the `build` chain.
- Its stage step (line 111) is:
  ```
  git add index.html api/ data/ stats.json feed/ journal/dispatches/feed.xml .well-known/llms-full.txt llms-full.txt
  ```
  `api/` covers the **producer**. Nothing in that list covers `.cache/`, so the **consumer is never staged.**

So every 4 hours the cron can commit a new `api/funnel-summary.json` while leaving the
git-tracked `.cache/cta-readiness.json` at its previous value. `check-cta-readiness --check`
compares `ready` and `shown` (it correctly strips the wall-clock `generatedAt`), so this is not
timestamp churn — it is a real, load-bearing value divergence.

Measured on the current tree:

| field | committed | regenerated |
|---|---|---|
| `shown` | 3 | **0** |
| `rate` | 0 | `null` |
| `reason` | waiting for 17 more | waiting for **20** more |

**Fix:** stage `.cache/cta-readiness.json` in the cron alongside the feed it is derived from.

## A3 · P1 · The readiness message promises a cumulative count the denominator never provides

> **Correction to a first pass of this audit.** I initially wrote that the threshold was *"unreachable
> by construction."* That was an overclaim and is withdrawn. `api/funnel-summary.json` carries
> `asOf: 2026-07-02` — source-derived from the newest RUM row, **not** wall-clock — so the epoch does
> not sit 52 days behind a sliding window as I first reasoned. If RUM data resumes, the window slides
> forward from the epoch and 20 impressions inside one 30-day window would satisfy it. The defect
> below is real, load-bearing, and narrower than "impossible". The corrected version is what ships.

This is why A1's numbers move at all, and it is a truth defect independent of the strand.

**Verified.** `scripts/check-cta-readiness.mjs` declares:

```js
'play-next': { minShown: 20, since: '2026-07-02', … }
reason: `waiting for ${rule.minShown - shown} more true-viewport post-epoch impressions`
```

That wording and that `since` promise a **cumulative count of impressions since the epoch**.
The number it reads is not that. `scripts/rollup-rum-ux.mjs` computes it over a rolling window:

```js
const WINDOW_DAYS = 30;                                    // line 41
// `epoch` only TIGHTENS the window; it never widens past WINDOW_DAYS.   // line 57
```

Two things follow, and both are measurable rather than inferred:

**1. The threshold is windowed, not cumulative.** Reaching `minShown: 20` requires 20 impressions
**inside a single 30-day window** — not 20 accumulated since July 2, which is what *"waiting for 20
more true-viewport post-epoch impressions"* plainly says. Those are materially different bars, and the
harder one is the real one. A reader budgeting for the stated bar will wait indefinitely for a
milestone the arithmetic never promised.

**2. Right now the effective post-epoch observation span is one day, and the evidence is frozen.**
`api/funnel-summary.json` reports `asOf: 2026-07-02` and `dataWindow: 2026-06-05 → 2026-07-02`. The
epoch (`2026-07-02`) **equals `asOf`**, so the epoch tightens the 30-day window down to its final day.
`shown` is not "impressions in the last 30 days" — it is "impressions on 2026-07-02". And `asOf` has
not advanced in 52 calendar days, which is consistent with the independently-flagged RUM staleness
(`rum-anomaly-canary`: latest `2026-08-13`; `TASK_BOARD:42`: the engagement history file has never
existed). The surface reports a confident *"waiting for 20 more"* while the data behind it has not
moved at all.

**This has already cost real time.** `context/TASK_BOARD.md:127` has parked the play-next conversion
redesign since S249 with *"once the honest window has data — let ~1 week of honest viewport-view vs
click data accrue, THEN decide"*. No amount of waiting advances a frozen `asOf`, and the bar being
waited on was never the bar actually enforced.

**Fix — and explicitly NOT by lowering the floor.** `TASK_BOARD:42` and the repo's own canon are
emphatic: *"Do not lower a floor to make the page look alive."* Lowering `minShown`, widening
`WINDOW_DAYS`, or moving the epoch to manufacture a verdict would all be the dishonest fix, and none
are done here. The honest fix is to make the artifact **say what it is actually measuring**:

- carry `windowDays` and `observedThrough` (the funnel's own `asOf`) onto the readiness row;
- state the requirement as *"within a single N-day window"* rather than a bare *"N more"*;
- when the epoch is at or after `observedThrough` — i.e. there is no post-epoch observation span yet —
  report that plainly instead of a confident countdown.

Every added field is source-derived (`funnel.asOf`, `funnel.windowDays`), so the artifact stays
byte-reproducible and the `--check` comparison stays honest. No wall-clock value enters the compared
set. That converts a silently-parked task into a visible decision the founder can actually make.

## A4 · P2 · Dead phantom-suppressor in the genius list, keyed to an epoch its sibling gate defines as wrong

**Verified, and provable rather than inferred.** `scripts/generate-genius-list.mjs:179` suppresses the
"re-evaluate play-next rotation" task with:

```js
if (playNext?.since === '2026-06-18' && Number(playNext?.counts?.shown || 0) === 0) return true;
```

The live value of `playNext.since` is **`2026-07-02`**. The `2026-06-18` literal is stale.

What makes this provable rather than a judgement call: the sibling gate
`scripts/check-play-next-impression-contract.mjs` pins `EXPECTED_EPOCH = '2026-07-02'` (line 18) and
its own self-test at line 56 uses **`'2026-06-18'` as the wrong-epoch negative control** — the exact
value the suppressor is keyed on. One script suppresses on the value another script's test suite
defines as the failure case.

The `shown === 0` half of that condition is now satisfied (A1/A3), so the epoch literal is the *only*
thing preventing the suppressor from firing.

**Honest scoping:** the guarded task does not currently appear in `docs/GENIUS_LIST.md`, so this is
**latent, not an active phantom** — a correctness fix with no present user-visible symptom. Ranked
P2 accordingly, and it should not be reported as a live bug that was fixed.

**Fix:** key the suppressor to the same epoch constant its sibling gate already exports, so the two
cannot drift apart again.
